# Аудит производительности, безопасности и UX — 5 октября 2026

Проверены оба репозитория: Go-ядро и React-интерфейс. Исправлены подтверждённые источники лишней работы CPU, выделений памяти, зависших процессов и соединений. Изменения проверены на настоящих PostgreSQL и FFmpeg, с браузерными экспортами MP4/MP3. Качество кодирования и точность границ не снижались ради скорости.

Исправленное ядро: `e9b4bb15734a08a897e85c171b8692b0cd658b55`; эта ревизия закреплена в `core.version` для CI и сборки интерфейса. Изменения аудита зафиксированы в обоих репозиториях. Развёртывание не выполнялось.

В конфигурации размещения API/worker дополнительно отключена запись в корневую файловую систему, удалены capabilities, ограничены PID и временная файловая система. Запись медиа остаётся в предназначенном для неё томе. Эти настройки проверены синтаксически; полный запуск собранного образа с ними пока не подтверждён.

## Измерения CPU и памяти

Сравнения относятся к конкретным операциям и синтетическим сценариям. Они не означают такое же ускорение полного экспорта или сокращение всей RAM сервера.

| Сценарий | До | После |
|---|---:|---:|
| Разбор HLS, 10 000 сегментов, медиана 3 прогонов | 24,84 мс | 11,35 мс |
| Выделенные байты при этом разборе | 10,42 МБ | 4,81 МБ |
| Поиск короткого окна в 100 000 сегментов | 158,89 мкс | 0,041 мкс |
| Проверка нового ключа при насыщенной таблице лимитов | 133–181 мкс | 0,078–0,079 мкс |
| JSON FFprobe для файла с тегом 1 МиБ | 1 051 270 Б | 293 Б |
| Перерисовки всего App за 15 секунд playback | 99 | 0 |
| Записи черновика за тот же интервал | 99 | 14 |
| Переподключения keydown за тот же интервал | 99 | 0 |

HLS-разбор в этом примере быстрее примерно на 54% и выделяет примерно на 54% меньше байтов. Шкала сохраняет прежнюю частоту обновления: 99/100 тиков в сравниваемых запусках. Счётчики React сняты в development-сборке с одинаковым управляемым плеером.

Отдельный профиль **production-сборок**, Chromium, три пары A/B с медианами:

| Измерение за 15 секунд / 100 тиков | До | После |
|---|---:|---:|
| Время задач главного потока, CDP TaskDuration | 342 мс | 163 мс |
| Время выполнения JavaScript | 240 мс | 59 мс |
| Выборочно измеренные JS-аллокации | 13,20 МБ | 0,986 МБ |
| JavaScript heap после сборки мусора | 4,12 МБ | 3,72 МБ |

Плеер в этом профиле управляемый, без настоящего внешнего iframe и декодирования видео. Выборочное измерение памяти само добавляет нагрузку; параллельные проверки браузера добавляли шум. Сокращение heap около 9,6% относится только к JavaScript этой страницы после GC, не к общей памяти браузера. [Сырые результаты](audit-data/2026-10-05-playback-profile.json) сохранены вместе с отчётом.

Обход 10 000 файлов показал 41,07 → 39,41 мс и 5,47 → 5,15 МБ выделений. Разница времени мала и не заявляется как надёжное ускорение. Основное улучшение — ограниченный размер одновременно удерживаемой порции записей каталога. Выделенные байты за операцию не равны пиковому RSS.

Сжатый JavaScript-пакет изменился с 133,85 до 134,90 кБ: работающие исправления и восстановление удаления добавили около 1 кБ. Уменьшение сетевого размера пакета этим аудитом не заявляется. Настройки качества FFmpeg не менялись; более быстрый профиль уже существовал до аудита.

## Поведение сохранения и UX

Черновик записывается обычно в течение 300 мс после редактирования; обновления позиции — с интервалом до секунды. Если таймер playback уже запущен, следующий структурный edit может ждать остаток этой секунды. Уход со страницы, скрытие вкладки и размонтирование немедленно сохраняют ожидающее состояние. Ключ повторного экспорта и его актуальный запрос сохраняются до отправки. При аварийном завершении браузера без lifecycle-событий возможна потеря последней секунды изменений.

Восстановление удаления доступно до следующего изменения списка/выделения/названия или ухода с шага «Фрагменты». Оно хранит не более двенадцати небольших записей, сохраняется при переключении языка и не может восстановить фрагменты поверх другого видео. Клавиатурный фокус после восстановления возвращается к выбору всех фрагментов. При активном импорте/экспорте переключение способа открытия источника отключено, чтобы название операции не расходилось с действительным запросом.

Изменения опираются на [эвристики Nielsen Norman Group](https://www.nngroup.com/articles/ten-usability-heuristics/): контроль действий, восстановление после ошибок, видимость состояния и предупреждение ошибок. Связь сообщений с элементами формы и обратная связь сверены с [W3C WAI](https://www.w3.org/WAI/tutorials/forms/notifications/). Это проверка конкретных сценариев, не сертификация всей доступности продукта.

## Проверки и доказательства

- **Go:** 119 самостоятельных тестов; 330 с учётом вложенных проверок. Полный `-race -count=1` с PostgreSQL и FFmpeg прошёл без пропущенных тестов. `go vet ./...` и сборка прошли. У публичного `pkg/engine` по-прежнему нет отдельного набора тестов; используются проверки общих операций и CLI.
- **Интерфейс:** 63 unit-теста, проверка типов и production-сборка прошли.
- **Браузеры:** итоговый набор desktop/mobile — 45 успешных сценариев и четыре явных opt-in пропуска. Chromium и Firefox отдельно прошли по 280 измеряемых состояний экранов, языков и тем: суммарно 560. Проверены реальные MP4/MP3, первые кадры и длительность, отмена, смена источника, восстановление после перезагрузки, ошибочные настройки, потерянный ответ экспорта, клавиатура, touch и изоляция сессий.
- **Производительность:** сохранён браузерный regression, проверяющий частоту записей, точную сохранённую позицию после flush/reload и отсутствие ненужного polling. Go benchmarks находятся рядом с соответствующими тестами.
- **Зависимости:** `govulncheck` и полный `npm audit` не обнаружили известных уязвимостей. Это не доказательство отсутствия неизвестных ошибок.
- **Размещение:** семь проверок активации/отката, разбор Compose и проверка Caddy прошли. Сборка полного Docker-образа остановилась из-за отказа соединения с настроенным сетевым proxy при получении Debian-пакетов; runtime smoke новых ограничений изоляции не подтверждён.
- **Безопасность:** проверены SSRF/DNS/redirect/HLS-ограничения, владение файлами, CSRF, SQL/path/command injection и границы subprocess. Подтверждённого обхода владения или SSRF в проверенных сценариях не найдено; исправлены описанные выше проблемы исчерпания ресурсов.

[Сводка машинных результатов](audit-data/2026-10-05-validation.json) содержит точные счётчики. Функциональный браузерный отчёт сохранил `passed`, 0 неожиданных ошибок и 0 flaky; оболочка после полной успешной сводки вернула 143. Это отмечено отдельно от результатов 45 завершённых проверок. Chromium-матрица использовала первоначальный локальный бинарник ядра; итоговая функциональная матрица и Firefox — пересобранное ядро со всеми исправлениями.

Первый функциональный прогон получил `storage_full` у одного экспорта: свободное место рабочего окружения оказалось около требуемого резерва в 1 ГиБ. После изменения **только временного тестового стенда** на 64 МиБ для небольших фикстур весь набор прошёл. Проверки лимитов и настройки проекта не ослаблялись. Firefox использовал уже имеющиеся изолированные библиотеки кодеков тестового окружения. Один первоначальный Go-запуск пересёкся с изменением тестового файла; приведённые выше результаты относятся к повторному полному запуску после фиксации исходников.

## Оставшиеся ограничения и следующий приоритет

1. **Свободное место рабочего окружения.** Во время проверки свободное место опускалось примерно до 626 МБ на диске 79 ГБ. При стандартных резервах это закономерно блокирует новые задания. Временные медиа, тестовая БД и процессы этого аудита удалены после проверки; свободное место восстановилось примерно до 1,2 ГБ (занято 99%). Отчёты сохранены, посторонние файлы не удалялись. Необходим отдельный разбор роста диска. Состояние производственного сервера этим измерением не определяется.
2. **Реальная нагрузка FFmpeg.** Основные затраты обычного экспорта остаются в декодировании, кодировании и сети. Общий RSS контейнеров и производительность конкретного рабочего видео под серверной квотой не измерялись. Следующий полезный профиль — реальные типовые исходники и длины клипов с одновременным измерением CPU, peak RSS, времени и размера результата.
3. **Рост хранилища.** Проверка размера остаётся O(число файлов), а очистка хранит множество зарегистрированных путей. Пакетное чтение уменьшает пиковое удержание каталога, но не заменяет учёт объёма/квоты файловой системы. Кешировать квоту без корректной инвалидации здесь небезопасно.
4. **Архитектура одного API и одного worker.** Квоты, лимиты и пул не превращены в распределённую систему. Четыре DB-соединения — ограниченный default, который можно изменить через DSN после нагрузочного измерения. Общий IP-лимит разделяется пользователями одного NAT.
5. **Изоляция внешних инструментов.** Guarded proxy не заменяет сетевую изоляцию на уровне ОС. Новые ограничения контейнера требуют реального запуска собранного образа перед выпуском.
6. **Предел браузерного покрытия.** Safari/WebKit и физические мобильные устройства не проверены. Четыре сценария с внешними/трёхчасовыми видео требуют явных входных источников и пропущены. Проверки управляемого YouTube подтверждают поведение UI, а не доступность конкретного ролика на площадке.

## Воспроизведение

В отдельных `core` и `web` репозиториях:

```sh
# core; TEST_DATABASE_URL должен указывать на отдельную тестовую БД
go test -race -count=1 ./...
go vet ./...
GOMAXPROCS=4 go test ./internal/app -run '^$' \
  -bench 'HLSParse|HLSSelect|StorageAdmission|RateLimitAtCapacity' -benchmem -count=3

# web; необходимы настоящий локальный API/worker и браузеры Playwright
npm test
npm run build
npm run test:deploy
npm run test:e2e -- --project=desktop --project=mobile
npm run test:e2e -- --project=layout-chromium --project=layout-firefox

# Изолированный профиль UI против уже обслуживаемой production-сборки
PROBE_URL=http://127.0.0.1:4173 node scripts/profile-playback.mjs
```

Сценарий профиля подменяет только тестовый источник и плеер в отдельном браузерном контексте; реальную серверную обработку он не измеряет. Счётчики имён компонентов в минифицированной production-сборке не применимы; для неё используются CDP-время и heap sampling. Для сравнения нужны одинаковые окружение, фикстуры и настройки обеих версий.
